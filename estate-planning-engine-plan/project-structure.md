## Key Design Decisions Explained

### Why `features/` folder?
- Clear ownership of business domains.
- Easy to move a feature to its own package later.
- `intake/` and `documents/` are the two most complex domains — they get their own rich sub-structure.

### Why separate `(dashboard)` and `(client)` route groups?
- Different layouts and auth requirements.
- Client intake can be a simpler, focused experience (progress bar, conversational mode).
- Attorney dashboard is data-dense with tables and actions.

### Why Zustand + TanStack Query + XState together?
- **XState**: Complex, long-lived, branching workflow (questionnaire) — needs visual debugging and guaranteed determinism.
- **Zustand**: Simple cross-component state (current firm, sidebar open/closed).
- **TanStack Query**: Everything that comes from or goes to the server (clients list, document history, session data).

### File Naming Conventions
- `*.machine.ts` — XState machines
- `*.generator.ts` / `*.service.ts` — Business logic that is not a React component
- `use*.ts` — Custom hooks
- `*.schema.ts` — Zod schemas (co-located with the feature)

### Environment Variables Strategy
Create `.env.example` with clear comments:

```env
# Clerk
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=
CLERK_SECRET_KEY=
CLERK_WEBHOOK_SECRET=

# Neon Postgres
DATABASE_URL=

# Vercel AI / Grok
GROK_API_KEY=                    # or OPENAI_API_KEY if using fallback

# Storage
SUPABASE_URL=
SUPABASE_SERVICE_ROLE_KEY=

# Emails
RESEND_API_KEY=

# Inngest (optional early)
INNGEST_EVENT_KEY=
INNGEST_SIGNING_KEY=
```

---

**This structure scales** from solo developer to a small team without major refactors. It also maps cleanly to how Grok and Cursor like to generate code (feature-focused prompts work extremely well).
